# 体验优化方案

## 现状问题

1. **启动慢**：页面加载后，`init()` 立即请求 `/api/sessions?limit=200`，获取全部会话后再渲染侧栏。200 个会话全部展开，DOM 节点过多，渲染耗时。
2. **切换卡顿**：每次点击会话都重新请求 `/api/sessions/<id>`，即使刚看完切回来也要重新加载。
3. **信息过载**：所有文件夹默认全部展开，用户需要看到所有项目的所有对话，但实际关心的只有近期活跃的。

## 修改方案

### 一、文件夹默认折叠

**目标**：只有近 1 天有更新的文件夹才自动展开，其余默认折叠。

**方案**：
- 后端：`GET /api/directories` 返回的每个目录增加 `recently_active` 布尔字段（`time_updated > now - 24h`）
- 前端：`renderSidebar()` 中，仅对 `recently_active = true` 的目录设置展开（`display: ''`），其余默认折叠（`display: 'none'`）
- 用户仍可手动点击文件夹头展开/折叠

**改动范围**：
- `app.py`：修改 `/api/directories` 端点，增加 `recently_active` 字段
- `static/js/app.js`：修改 `renderSidebar()`，根据 `recently_active` 控制初始展开状态

### 二、会话详情懒加载 + 缓存

**目标**：点击会话时才加载消息，切换回来后不重复请求。

**方案**：
- 新增全局对象 `SESSION_CACHE = {}`，key 为 sessionId，value 为 API 返回的数据
- `openSession(id)` 逻辑改为：
  1. 如果 `SESSION_CACHE[id]` 存在，直接渲染缓存数据（`renderSessionFromCache()`）
  2. 如果不存在，显示 loading，请求 `/api/sessions/<id>`，存入缓存，再渲染
- 页面刷新后缓存自然消失
- 如果用户在当前会话发了一条新消息（`sendMessage`），清空 `SESSION_CACHE[id]` 并重新加载（因为消息已变化）

**注意点**：
- 发送消息/撤销后需要清除缓存，确保下次打开看到最新数据
- 对比模式（`doCompare`）也应当使用缓存的 `SESSION_CACHE`

**改动范围**：
- `static/js/app.js`：
  - 新增 `SESSION_CACHE = {}`
  - 修改 `openSession()` 加入缓存逻辑
  - 修改 `sendMessage()` done 后清除缓存
  - 修改 `undoLastAction()` 后清除缓存
  - 修改 `doCompare()` 使用缓存

### 三、展开/折叠状态优化

**目标**：减少 DOM 操作，提升侧栏渲染性能。

**方案**：
- 当前 `renderSidebar()` 每次搜索或切换都全量重建 HTML。实际上搜索后只需要更新 group 内的 session 列表
- 简单优化：保留展开/折叠状态的 `display` 属性，`renderSidebar()` 重建时恢复状态
- 更进一步的优化：搜索时只更新 session-item 的显示/隐藏，不重建整个侧栏（后续可做）

**当前改动范围**：
- `static/js/app.js`：在 `renderSidebar()` 中重建后根据 `recently_active` 设置初始折叠状态

## 涉及文件

| 文件 | 改动 |
|------|------|
| `app.py` | `/api/directories` 增加 `recently_active` 字段 |
| `static/js/app.js` | `SESSION_CACHE`、`renderSidebar()` 折叠逻辑、`openSession()` 缓存逻辑、`sendMessage()`/`undoLastAction()` 清除缓存 |

## 不在此方案中的优化

- 搜索时增量更新侧栏（只隐藏/显示匹配项，不重建 DOM）：后续可做，但复杂度较高
- 虚拟滚动（只渲染可见的 session-item）：后续可做，当前 200 个对话页面加载约 1-2 秒，可接受
- 分页加载侧栏会话（先加载 50 条，滚动到底部再加载更多）：后续可做
